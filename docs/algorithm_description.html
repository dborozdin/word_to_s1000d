4.3. Определение границ элементов

Для каждого элемента отслеживаются позиции в документе:

  • start_line, start_char — начало элемента
  • end_line, end_char — конец элемента
  • start_para, end_para — индексы параграфов

Особые случаи:

  • Нумерованные заголовки с «хвостом»: если после заголовка в том же параграфе есть текст (разделённый \n), первая строка → header, остальное → paragraph
  • Списки: начало — первый элемент; конец обновляется через _update_list_end_para() при завершении списка
  • Таблицы: число строк аппроксимируется как число «строк»; char_position сбрасывается после таблицы

8. Разметка в PDF (левая панель)

Текущая реализация

8.1. Извлечение текстовых блоков (серверное, PyMuPDF)

Функция extract_pdf_blocks() в comparison_app/pdf_block_extractor.py:

  1. Открытие PDF через fitz (PyMuPDF)
  2. Извлечение raw текстовых блоков с bounding boxes (x0, y0, x1, y1)
  3. Обнаружение и удаление повторяющихся колонтитулов
  4. Разбиение/слияние блоков по эвристикам:
    • Зазор между строками > 1.6× минимальный зазор → разделить
    • Сдвиг отступа влево или значительный вправо → разделить
    • Терминальная пунктуация (конец предложения) → разделить
    • Маркер списка (тире/буллет) в начале строки → всегда разделить
    • Изменение размера шрифта > 25% → разделить

Результат: JSON {page_num, blocks: [{x0, y0, x1, y1, text, max_font_size}, ...]}

API endpoint: /api/pdf-blocks/<dmc>

8.2. Клиентский fallback (pdf.js)

Если серверное извлечение недоступно — pdf.js извлекает текст на клиенте, группирует по Y-позиции, классифицирует по размеру шрифта и паттернам.

8.3. Визуализация аннотаций

  • Для каждого блока создаётся <div class="anno-marker"> с позицией в % от страницы
  • Цветовая циклическая палитра из 10 цветов (ANNO_COLORS)
  • Метка: аббревиатура типа + индекс (например, «пар. 5»)
  • Стиль: скобки-brackets слева от блока
Ключевой момент: PDF-блоки извлекаются независимо от XML. Они содержат только позиции и текст — без типов элементов. Количество PDF-блоков и XML-элементов почти никогда не совпадает (например, PDF: 50 блоков, XML: 35 элементов). Мостом между ними служит эталон (reference).

9.3. Синхронизация индексов с эталоном

Рендерер назначает data-anno-idx последовательно (1, 2, 3…), но в эталоне индексы могут иметь разрывы из-за элементов с типом _skip. Функция _syncS1000dElements() (в comparison.js) переназначает индексы правой панели по эталону:

  • Перебирает элементы эталона в порядке idx
  • Пропускает _skip элементы без потребления DOM-слотов (в XML они удалены)
  • K-му DOM-элементу правой панели назначается idx K-го не-skip элемента эталона

Это обеспечивает совпадение data-anno-idx между панелями, что делает навигацию (« / ») корректной — обе панели прокручиваются к одному и тому же сопоставленному элементу.

9.4. Составная нумерация элементов

Формат метки элемента: <тип><номер_типа> [абсолютный_индекс]

Пример: пар.3 [5] — 3-й параграф в документе, абсолютный индекс 5.

Per-type счётчики ведутся отдельно для каждой панели, что позволяет визуально сравнить количество элементов каждого типа между PDF-разметкой и сгенерированным XML.

10.2. Инициализация (автоматическая) — XML-first подход

При первом открытии сравнения (или после нажатия «Сбросить эталон») эталонная разметка создаётся по приоритету:

  1. XML-first (приоритет 1, element_source=hybrid + наличие XML + MS Word):
    1. Извлекает XML-элементы из сгенерированного XML — extract_xml_elements(xml_path)
    2. Загружает stable_id из sidecar JSON (user_finetune/*_element_map.json)
    3. Рендерит DOCX → PDF и извлекает блоки — extract_pdf_blocks_full()
    4. Матчит XML-элементы к PDF-блокам — match_xml_to_pdf() в parsers/hybrid_matcher.py
    5. Результат: эталон с теми же элементами что и XML, позиционированными в PDF-пространстве
    6. Источник: source: "auto_xml_derived"
  2. Hybrid PDF+DOCX (приоритет 2, element_source=hybrid + MS Word): PDF-first матчинг, match_pdf_to_docx(), source: "auto_hybrid"
  3. DOCX-only (приоритет 3, fallback): mammoth HTML-парсер, source: "auto"
Алгоритм match_xml_to_pdf()

XML-элементы — «якоря», PDF-блоки — «позиции». Двухпроходная стратегия:

Pass 1 — оконный поиск с сохранением порядка документа:

  1. Для каждого XML-элемента поиск PDF-блока по текстовому сходству в окне [cursor-3 .. cursor+80]. Нормализация (_normalize_for_match): убираются буллеты (-, •) и одноуровневая нумерация (1., 1)), но многоуровневые префиксы (3.1.2, 3.2.5) сохраняются для различения элементов списков с одинаковым текстом. _type_context_factor штрафует warning/caution/note при отсутствии ключевых слов (×0.1). Безопасность: max(normalized, raw) score гарантирует надёжность начального матчинга.
  2. Расширение вперёд (forward expansion): захват последовательных PDF-блоков. Критерии остановки:
    • is_table guard: не-табличный XML-элемент не может захватить PDF-блок с is_table=True.
    • Граница страниц: не более anchor_page + 1.
    • Boundary ownership: ни один другой XML-элемент не претендует на блок с confidence >0.4.
    • Y-gap: <3× медианного (для списков — <5× медианного). Исключение: если следующий блок находится перед переходом страницы (footer/header), gap-break пропускается для продолжения на следующей странице.
    • X-offset: ±40 px или блоки вертикально близки на той же странице (line-wrap, gap <1.5× медианного). При переходе страниц: таблицы продолжаются без ограничений; для остальных — порог 100 px.
    • text_end match: prefix_score(text_end, block) > 0.4 → конец элемента.
    Сохранение многоуровневых чисел в нормализации предотвращает ложные срабатывания boundary-check для списков с похожим текстом (3.1.1 vs 3.1.4).
  3. Слияние захваченных блоков: один элемент эталона с span=N и объединённым bbox.

Pass 2 — глобальный поиск для элементов, не найденных в Pass 1 (warnings/cautions могут стоять в начале XML, но физически на последних страницах PDF, за пределами окна Pass 1; также элементы «застрявшие» из-за cursor jump):

  1. Каждый не-найденный XML-элемент ищет по ВСЕМ свободным PDF-блокам (без ограничения cursor/window).
  2. Forward expansion полностью идентична Pass 1 (все критерии остановки, включая is_table guard, cross-page relaxation, page-bottom peek).

Sentinel-типы:

  • PDF-блоки без XML-соответствия → тип _extra_pdf (красная штриховка).
  • XML-элементы без PDF-позиции → тип _unmatched_xml с интерполированным bbox (жёлтая штриховка).
  • При apply_reference_markup() и сравнении sentinel-типы фильтруются: _extra_pdf, _unmatched_xml, _skip не участвуют в матчинге.

11.1. Общий workflow

Одно-проходный процесс, управляемый из verify_loop.py:

  1. Загрузка эталона из _references/{dmc}.json
  2. Очистка overrides (для backward compatibility)
  3. Конвертация DOCX → XML с применением эталонной разметки
  4. Сравнение с эталоном (LCS-алгоритм)
  5. Валидация XML по XSD
  6. Маппинг ошибок XSD обратно на элементы

11.2. Применение эталонной разметки

Функция apply_reference_markup() в parsers/elements_analyzer.py:1151-1329:

  1. Для каждого ref-элемента ищется лучшее совпадение среди авто-извлечённых по сходству текста (prefix scoring)
  2. Тип из эталона подставляется IN-PLACE (без переупорядочивания элементов)
  3. Элемент помечается метаданными:
    • _ref_annotated: True — тип пришёл из эталона
    • _original_type — исходный авто-определённый тип
    • _ref_idx — индекс в эталоне
    • _ref_type_raw — тип из эталона (сырой)
  4. Если для элемента нет совпадения в эталоне — остаётся авто-определённый тип
  5. Фильтрация sentinel-типов: элементы с типами _extra_pdf, _unmatched_xml исключаются перед матчингом, чтобы не «красть» DOCX-элементы у настоящих ref-элементов.
  6. Pre-merge: если несколько последовательных DOCX-элементов имеют одинаковый _ref_idx и тип из множества {paragraph, warning, caution, note}, они объединяются в один элемент с конкатенированным контентом (через \n). Для warning/caution результат генерируется как несколько <warningAndCautionPara>, для note — несколько <notePara>.

11.3. Сравнение: 3-фазный алгоритм на stable_id

comparison_app/headless_comparator.py

Алгоритм сопоставления элементов эталона (ref) и сгенерированного XML работает в 3 фазы:

  1. Фаза 1 — прямое сопоставление по stable_id: Если у элемента ref и элемента XML совпадает stable_id (content-hash ID) → пара найдена. Это наиболее надёжный метод, не зависящий от порядка элементов или корректности типов.
  2. Фаза 2 — контентное сопоставление: Для оставшихся (без совпавшего stable_id) — сопоставление по текстовому сходству через difflib.SequenceMatcher с порогом 0.4. Сравниваются text_start + text_end.
  3. Фаза 3 — LCS fallback: Для элементов, не сопоставленных в фазах 1–2, выполняется LCS по последовательности типов (для обратной совместимости со старыми эталонами без stable_id).

Score = 0.4 × match_ratio + 0.3 × type_correctness + 0.3 × avg_text_similarity

  • match_ratio — доля сопоставленных элементов (все 3 фазы)
  • type_correctness — доля пар, где тип ref совпал с типом XML
  • avg_text_similarity — среднее текстовое сходство по всем парам
  • Диапазон: 0.0 – 1.0

Преимущество перед старым LCS-алгоритмом: одна ошибка классификации типа (например, параграф → список) больше не вызывает каскадный сдвиг всех последующих элементов. Текст совпадает → пара найдена → ошибка типа учитывается отдельно в type_correctness (30%).

11.4. Маппинг XSD-ошибок

Функция _map_xsd_to_source_elements() в verify_loop.py:51-95:

  • Текстовое сопоставление (prefix, 3-20 символов)
  • Для каждой ошибки — определение:
    • is_user_annotated — элемент пришёл из эталона?
    • user_type — тип по эталону
    • original_type — авто-определённый тип (до override)
    • ref_idx — индекс для навигации

11.5. Отображение результатов

  • Зелёный если score ≥ 95%, жёлтый если ниже

V.4. Уникальная идентификация элементов

Проблема

Текущая идентификация — порядковый idx (1, 2, 3, ...). Он нестабилен: при перегенерации PDF блоки могут сместиться, и idx перестанет соответствовать тому же элементу. Кроме того, два элемента с 100% одинаковым текстом неразличимы.

Решение: составной element_id

// Формула element_id = sha256( page_num // страница (1-based) + "|" + round(y_position, -1) // y-позиция, квантованная до 10 единиц + "|" + text[:30].strip().lower() // первые 30 символов текста (нормализованы) )[:12] // первые 12 hex-символов для компактности

Свойства

СвойствоОбеспечение
Устойчивость к перерендерингу y_position квантуется до 10 единиц PDF — мелкие сдвиги не меняют hash
Различение одинаковых текстов Разные page_num или y_position → разный hash
Обратная совместимость Порядковый idx сохраняется параллельно для работы со старыми reference JSON
Merge element_id первого (верхнего) элемента сохраняется как id объединённого
Split Новые element_id генерируются для дочерних элементов по их позициям

Матчинг в reference

  1. Сначала поиск по element_id (точное совпадение)
  2. Если не найден — fallback на idx + text_start/text_end (текущий алгоритм)
  3. При следующем сохранении reference — element_id добавляется автоматически

V.6. Обработка таблиц и иллюстраций

Таблицы и иллюстрации — особый случай: PDF не содержит их в виде отдельных блоков.

Таблицы

  1. Структура — из DOCX: ячейки, строки, заголовки (через table_parser.py)
  2. Позиция — определяется по окружающим PDF-блокам:
    • Найти последний PDF-блок перед таблицей (по тексту предыдущего DOCX-элемента)
    • Найти первый PDF-блок после таблицы (по тексту следующего DOCX-элемента)
    • bbox.y0 = prev_block.y1 + gap
    • bbox.y1 = next_block.y0 - gap
  3. Маппинг: тип 0:1 — таблица вставляется между PDF-блоками

Иллюстрации

  1. Файл — из DOCX: a:blip элемент, извлечённый illustration_parser.py
  2. Позиция — аналогично таблицам: интерполяция между соседними PDF-блоками

Часть VI. Стабильные идентификаторы элементов (stable_id)

Система stable_id обеспечивает робастное сопоставление элементов между PDF-эталоном и сгенерированным XML, устойчивое к ошибкам классификации типов и XSD-переупорядочиванию.

Проблема позиционного сопоставления

Старый алгоритм сопоставлял элементы по позиции внутри групп типов: K-й heading ↔ K-й heading, K-й paragraph ↔ K-й paragraph. При ошибке классификации типа (например, параграф → список) все последующие элементы этого типа «съезжали», и score переставал отражать реальное качество генерации.

Дополнительно: XSD-валидатор требует, чтобы <warning> и <caution> шли перед <para> внутри <levelledPara>. Это переупорядочивание нарушало позиционное соответствие DOCX → XML.

Решение: content-hash ID

parsers/elements_analyzer.py

Функция compute_stable_id(seq_index, element_type, text) генерирует 12-hex SHA-256 хеш:

raw = f"{seq_index}|{element_type}|{text[:80].strip().lower()}"
stable_id = sha256(raw)[:12]
  • Уникален даже для дублирующихся параграфов (индекс в хеше)
  • Стабилен при повторных конверсиях (текст не меняется)
  • Не требует модификации DOCX файлов
  • Вычисляется при парсинге DOCX в analyze_document_elements()
  • Сохраняется в эталоне _references/{dmc}.json (поле stable_id)

Sidecar JSON: передача ID в XML

processing_scripts/descriptive_processor.py

При генерации XML создаётся sidecar-файл DMC-..._element_map.json рядом с XML:

{"element_map": [
  {"seq": 1, "stable_id": "a1b2c3d4e5f6", "type": "heading", "text_start": "..."},
  {"seq": 2, "stable_id": "f6e5d4c3b2a1", "type": "para", "text_start": "..."},
  ...
]}

Алгоритм построения sidecar:

  1. Парсинг финального XML через extract_xml_elements() — получение элементов в том же порядке, в каком рендерер (S1000DHTMLRenderer) обходит XML-дерево
  2. Для каждого XML-элемента — поиск лучшего DOCX-элемента по текстовому сходству (SequenceMatcher, порог 0.3, бонус за совпадение типа)
  3. Присвоение stable_id от найденного DOCX-элемента

Это гарантирует, что последовательность sidecar точно соответствует счётчику аннотаций в рендерере (_anno_counter), даже после XSD-переупорядочивания.

comparison_app/s1000d_renderer.py

Рендерер загружает sidecar и для каждого элемента добавляет атрибут data-element-id="{stable_id}" в HTML. Это позволяет клиентскому JS сопоставлять элементы правой панели (XML) с эталоном по ID, а не по позиции.

Визуальная индикация качества сопоставления

comparison_app/static/js/comparison.js

Функция highlightMismatches() использует 3 уровня визуальной индикации:

УровеньУсловиеСтиль
Полное совпадение Тот же stable_id, тот же тип, схожий текст Без выделения
Контент совпал, тип отличается stable_id или текст совпали, но тип элемента различается Оранжевая пунктирная рамка (.anno-type-mismatch)
Не сопоставлен Элемент не нашёл пары ни по ID, ни по тексту Красная пунктирная рамка (.anno-mismatch)

Обратная совместимость

  • Эталоны без stable_id — fallback на LCS по типам (фаза 3 алгоритма сравнения)
  • XML без sidecar — рендерер не добавляет data-element-id, навигация работает через type-group matching (фаза 2 _syncS1000dElements())
  • Все существующие эталоны продолжают работать без модификации
