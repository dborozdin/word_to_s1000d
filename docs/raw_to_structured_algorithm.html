1. Что делает инструмент

Инструмент берёт обычную папку с документами Word, PDF и графикой — и автоматически раскладывает их в правильную двухуровневую структуру папок по стандарту S1000D. Каждая итоговая папка — это один модуль данных.

Процесс в двух шагах

1
Сырые документы → структурированные папки (этот инструмент) Читает имена файлов, определяет тип каждого документа, присваивает код DMC, создаёт папки и копирует файлы.
2
Структурированные папки → XML (следующий этап) Из структурированных папок генерируется S1000D XML.

Запуск — из веб-интерфейса (кнопка «Сгенерировать структуру») или из командной строки:

python raw_to_structured.py --input doc_source_12_raw --output doc_source_12_generated python raw_to_structured.py --input doc_source_12_raw --output doc_source_12_generated --validate <эталонная_папка>
ПараметрЧто указать
--inputПапка с исходными (сырыми) документами
--outputКуда положить результат
--validateЭталонная папка для проверки результата (необязательно)

2. Настройка через веб-интерфейс

Все пути и параметры можно задать прямо в браузере, не редактируя файлы вручную. Для этого используется диалог настроек и панель исходных документов на главной странице.

Панель исходных документов и кнопки запуска

На главной странице отображается информация о найденных исходных документах и кнопки для запуска преобразования:

Панель статистики исходных документов, индикатор pipeline и кнопки генерации

  • Исходные документы — показывает текущую папку и количество распознанных файлов по типам: описания, ТК, спецфайлы, рисунки.
  • Сгенерировать структуру — запускает преобразование сырой папки в двухуровневую структуру S1000D (этап 1).
  • Генерировать XML — запускает генерацию S1000D XML из структурированных папок (этап 2).
  • Генерировать все — выполняет оба этапа последовательно.

Диалог настроек

Открывается по нажатию на шестерёнку (⚙) в правом верхнем углу страницы.

3. Какие входные папки поддерживаются

Инструмент автоматически определяет, как организована входная папка, и работает с обоими вариантами:

Вариант А — по типам документов

Документы разложены по отдельным папкам: описания, технологические карты, рисунки.

doc_source_29_raw/ ├── Описания/ ← файлы описаний (Word) ├── Технология/ ← технологические карты (Word) ├── Рисунки/ ← графика (CDR, JPG, PNG) └── спецфайлы (ЛРВИ, ЛРИ, ПДС, ...) ← на верхнем уровне
Инструмент ищет папки, содержащие в названии слова «Описан», «Технолог», «Рисунк». Точное название не важно.

Вариант Б — по компонентам

Каждый компонент — в своей папке (по коду: система.подсистема.компонент). Внутри — все типы документов вместе.

doc_source_12_raw/ ├── 012.00.00/ ← описания, ТК, папка Рисунки/ │ ├── 012-00-00.doc описание │ ├── 012-21-00 ТК 1.doc технологическая карта │ └── Рисунки/ графика ├── 012.91.00/ ← технологические карты │ ├── 012.91.00 ТК 1.doc │ └── ... ├── 012.00.00 ЛРВИ.docx ← спецфайл на верхнем уровне └── ...
Если папок «Описания»/«Технология»/«Рисунки» на верхнем уровне нет, а есть папки вида NNN.NN.NN — включается этот режим.

Какие файлы игнорируются

Временные и служебные файлы пропускаются автоматически: ~$... (черновики Word), ~WRL..., Thumbs.db, desktop.ini, файлы *.tmp.

4. Как распознаются документы

Тип документа определяется по имени файла. В коде компонента допускаются как точки, так и дефисы — 029.11.01 и 012-00-00 равнозначны.

Тип документаКак выглядит имя файлаПримеры
Описание Код + «описание» / «обратный клапан» 029.11.01 описание гидрокомпенсатор.doc
Описание (без ключевого слова) Только код + расширение 012-00-00.doc, 012-02-01.docx
Технологическая карта (ТК) Код + «ТК» + номер 029.11.01 ТК 1 демонтаж.doc, 012.91.00 ТК 3.doc
ТК ТО Код + «ТК ТО» 029.00.00 ТК ТО.doc
Таблица Код + «Таблица» + номер 012-00-00 Таблица 1.doc
Рисунок Код + «рисунок»/«рис» + номер 029.00.00 рисунок 1.cdr
ПИУН Код + «ПИУН» 029.00.00 ПИУН.doc

Спецфайлы верхнего уровня

Документы, лежащие прямо в корне входной папки (не в подпапках), распознаются по ключевым словам в названии:

Для разработчика: regex-паттерны распознавания

Все паттерны определены в начале raw_to_structured.py. Разделитель кода — [.\-], т.е. точка или дефис.

КонстантаПаттерн
RE_DESCRIPTION^(\d{3})[.\-](\d{2})[.\-](\d{2})\s+(?:описани\S*|обратный\s+клапан)...
RE_PLAIN_DESCRIPTION^(\d{3})[.\-](\d{2})[.\-](\d{2})\s*\.(docx?|pdf)$ — только в компонентном режиме
RE_TK^(\d{3})[.\-](\d{2})[.\-](\d{2})\s+ТК\s*(\d+)\s*(.*?)...\.(docx?|pdf)$
RE_TABLE^(\d{3})[.\-](\d{2})[.\-](\d{2})\s+Таблица\s*(\d+)...\.(docx?|pdf)$
RE_GRAPHIC^0?(\d{2,3})[.\-](\d{2})[.\-](\d{2})\s+(?:рисунок|рис)\s*(\d+)...\.(cdr|jpg|png)$
RE_PIUN_GRAPHIC^(\d{3})[.\-](\d{2})[.\-](\d{2})\s+ПИУН\s+рис\s*(\d+)...\.(cdr|jpg|png)$
RE_COMPONENT_FOLDER^\d{3}\.\d{2}\.\d{2}$ — только для автодетекции режима

Порядок проверки в компонентном режиме: ТК ТО → ПИУН → Таблица → ТК → Описание (с ключевым словом) → Описание (только код). Первое совпадение побеждает.

Фильтрация мусорных файлов — функция _is_junk_file(): ~$*, ~WRL*, Thumbs.db, desktop.ini, *.tmp.

5. Что получается на выходе

На выходе — двухуровневая структура папок:

Уровень 1 — Компоненты

Одна папка = один компонент (агрегат, узел).

Формат имени: 029-11-01 - Гидрокомпенсатор

Уровень 2 — Модули данных

Внутри каждого компонента — папки модулей данных с DMC-кодом в квадратных скобках.

Формат имени: [S5-A-029-11-01-00A-040A-A] Гидрокомпенсатор. Описание устройства

doc_source_29_generated/ 029-00-00 - Гидравлическая система/ [S5-A-029-00-00-00A-005A-A] Гидравлическая система. Перечень принятых сокращений/ [S5-A-029-00-00-00A-040A-A] Гидравлическая система. Описание и принцип действия/ ... 029-11-01 - Гидрокомпенсатор/ [S5-A-029-11-01-00A-040A-A] Гидрокомпенсатор. Описание устройства/ [S5-A-029-11-01-00A-920A-A] Гидрокомпенсатор. Демонтаж и монтаж/ ...

6. Как формируется код модуля данных (DMC)

Каждый модуль данных получает уникальный код — DMC (Data Module Code). Он собирается из нескольких частей:

Пример: S5-A-029-11-01-00A-040A-A

Часть кодаЗначениеОткуда берётся
S5Код моделиНастройка (по умолчанию S5)
AКод отличийНастройка (по умолчанию A)
029СистемаПервые 3 цифры из имени файла
11ПодсистемаСледующие 2 цифры из имени файла
01КомпонентПоследние 2 цифры из имени файла
00AКод сборкиОбычно 00. Для ПИУН — 01–05. Для фильтров — 01

Для разработчика: формирование DMC в коде

DMC формируется функцией build_dmc_string() в raw_to_structured.py.

Особенность поля assyDisassyCode: если disassy_code != '00', используется disassy_code, иначе — assy_code. К нему всегда добавляется вариант A.

Настройки кода модели, отличий и расположения задаются в секции [raw_import] файла config.ini: model_ident_code, system_diff_code, item_location_code.

7. Как назначаются коды информации

Код информации (info-код) определяет тип содержания модуля данных: описание устройства, демонтаж, проверка и т.д.

  • Для описаний — всегда 040 (описание устройства и принципа действия).
  • Для ТК — определяется по ключевым словам в заголовке файла. Система ищет совпадение в таблице правил и выбирает правило с наивысшим приоритетом.

Таблица OVERRIDES в raw_to_structured.py — словарь, где ключ (system, subsystem, component, base_info_code). Функция apply_override() сначала ищет точное совпадение по 4 полям, затем — с подстановочным символом * вместо component.

8. Особые случаи

ТК ТО — один файл → три модуля

Файл «ТК ТО» (технологическая карта технического обслуживания) автоматически разбивается на 3 модуля данных. Один и тот же файл попадает в 3 папки:

КодНазвание модуля
012Меры безопасности
720Общие указания при монтаже фторопластовых рукавов
920Общие указания при проведении демонтажно-монтажных работ

ПИУН — один файл → пять модулей

Файл ПИУН (перечень используемых неисправностей) разбивается на 5 модулей данных с разными кодами сборки (01–05). Рисунки ПИУН привязываются к модулю по номеру: рис. 101 → 01, рис. 102 → 02 и т.д.

Фильтроэлементы

Если в названии ТК есть слово «фильтроэлемент», код сборки меняется с 00 на 01, а в имени компонента добавляется префикс «Фильтроэлемент».

9. Проверка результата по эталону

Если есть эталонная папка (созданная вручную или ранее проверенная), инструмент может сравнить свой результат с ней и показать расхождения.

Как происходит проверка

1
Сбор данных Обход папок обоих уровней в сгенерированной и эталонной структурах. Из имён папок второго уровня извлекаются DMC-коды.
2
Сравнение кодов Определяются: совпадающие DMC-коды, коды только в эталоне, коды только в результате.
3
Сравнение названий компонентов Коды папок первого уровня (до « - ») сравниваются точно. Названия (после « - ») сравниваются с допуском на мелкие различия (порог 85%).
4
Сравнение названий модулей Для совпадающих DMC-кодов сравниваются заголовки папок второго уровня с тем же порогом 85%.
Нечёткое сравнение названий учитывает: точное совпадение (после приведения к нижнему регистру), совпадение по началу (для обрезанных имён Windows) и похожесть текста (порог 85%).
Для разработчика: реализация валидации

Функция validate_against_reference() в raw_to_structured.py. Нечёткое сравнение — difflib.SequenceMatcher с порогом 0.85. Функция _names_match() реализует три стратегии: exact match, prefix match (для длинных путей Windows), fuzzy match.

Возвращает dict с полным отчётом: количество папок, совпавшие и несовпавшие DMC-коды, расхождения в именах. Используется в API-маршруте /api/generate-structure.
