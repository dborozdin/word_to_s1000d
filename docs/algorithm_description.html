4.3. Определение границ элементов

Для каждого элемента отслеживаются позиции в документе:

  • start_line, start_char — начало элемента
  • end_line, end_char — конец элемента
  • start_para, end_para — индексы параграфов

Особые случаи:

  • Нумерованные заголовки с «хвостом»: если после заголовка в том же параграфе есть текст (разделённый \n), первая строка → header, остальное → paragraph
  • Списки: начало — первый элемент; конец обновляется через _update_list_end_para() при завершении списка
  • Таблицы: число строк аппроксимируется как число «строк»; char_position сбрасывается после таблицы

5. Генерация XML

Генератор: generators/s1000d_generator.py

5.1. Базовая структура

Корневой элемент <dmodule> с пространствами имён: xsi, rdf, dc, xlink. Ссылка на XSD-схему через xsi:noNamespaceSchemaLocation.

5.2. identAndStatusSection

  • dmCode — все компоненты S1000D-кода
  • dmTitle — techName + infoName
  • language — ru/RU
  • issueInfo — 001/00
  • dmStatus — security, logo, companies, brexRef, applic

5.3. Content — Описательный модуль

Структура: <description> / <levelledPara> / [title + para|table|figure|note|randomList]

XSD-упорядочивание (строки 287-340): элементы внутри levelledPara пересортировываются:

  1. <title>
  2. <warning>
  3. <caution>
  4. <para> | <table> | <figure> | <note> | <randomList>
  5. Вложенные <levelledPara>

5.4. Content — Процедурный модуль

Структура: <content> / <procedure>

  • <preliminaryRqmts> — оборудование, расходные материалы, запчасти, требования безопасности
  • <mainProcedure> — рекурсивные процедурные шаги (<proceduralStep>)
  • <closeRqmts> — требования по завершению

6. Валидация по XSD

Сгенерированный XML валидируется через lxml против соответствующей XSD-схемы (xsd/descript.xsd или xsd/proced.xsd).

  • Пространства имён удаляются перед валидацией
  • Результат: список ошибок с номером строки, столбца, сообщением, тегом элемента, XPath

8. Разметка в PDF (левая панель)

Текущая реализация

8.1. Извлечение текстовых блоков (серверное, PyMuPDF)

Функция extract_pdf_blocks() в comparison_app/pdf_block_extractor.py:

  1. Открытие PDF через fitz (PyMuPDF)
  2. Извлечение raw текстовых блоков с bounding boxes (x0, y0, x1, y1)
  3. Обнаружение и удаление повторяющихся колонтитулов
  4. Разбиение/слияние блоков по эвристикам:
    • Зазор между строками > 1.6× минимальный зазор → разделить
    • Сдвиг отступа влево или значительный вправо → разделить
    • Терминальная пунктуация (конец предложения) → разделить
    • Маркер списка (тире/буллет) в начале строки → всегда разделить
    • Изменение размера шрифта > 25% → разделить

Результат: JSON {page_num, blocks: [{x0, y0, x1, y1, text, max_font_size}, ...]}

API endpoint: /api/pdf-blocks/<dmc>

8.2. Клиентский fallback (pdf.js)

Если серверное извлечение недоступно — pdf.js извлекает текст на клиенте, группирует по Y-позиции, классифицирует по размеру шрифта и паттернам.

8.3. Визуализация аннотаций

  • Для каждого блока создаётся <div class="anno-marker"> с позицией в % от страницы
  • Цветовая циклическая палитра из 10 цветов (ANNO_COLORS)
  • Метка: аббревиатура типа + индекс (например, «пар. 5»)
  • Стиль: скобки-brackets слева от блока
Ключевой момент: PDF-блоки извлекаются независимо от XML. Они содержат только позиции и текст — без типов элементов. Количество PDF-блоков и XML-элементов почти никогда не совпадает (например, PDF: 50 блоков, XML: 35 элементов). Мостом между ними служит эталон (reference).

10. Эталон (Reference) — мост между PDF и XML

Эталон — это «истинная» разметка документа, которая определяет, какие элементы и какого типа должны быть в итоговом XML.

10.1. Хранение

JSON-файлы в comparison_app/_references/{dmc_string}.json

// Пример структуры reference { "dmc_string": "DMC-S5-A-029-00-00-00A-012A-A_001", "docx_hash": "sha256:9b434fd550f2...", "created_at": "2026-02-16T21:10:55", "modified_at": "2026-02-18T10:30:29", "source": "auto+manual", "elements": [ { "idx": 1, "type": "heading", "text_start": "Первые 60 символов текста...", "text_end": "Последние 40 символов...", "span": 1 }, { "idx": 2, "type": "unnumbered_list", "text_start": "- первый пункт списка...", "text_end": "последний пункт.", "span": 5 // объединяет 5 DOM-блоков } ] }

10.2. Инициализация (автоматическая)

  1. Пользователь нажимает кнопку «Эталон»
  2. JS вызывает /api/reference/<dmc>/init (POST)
  3. Python: init_reference_from_auto() — извлекает элементы из docx через mammoth HTML-парсер
  4. Создаёт список элементов с авто-назначенными типами
  5. Сохраняет в _references/ с source: "auto"

comparison_app/reference_store.py

10.3. Редактирование (ручное)

Пользователь входит в режим редактирования → на блоках появляются цветные бейджи. Доступные операции через контекстное меню (правый клик):

ОперацияОписаниеЭффект на span
Смена типаВыбор из dropdown: para, heading, table, ...Не меняется
Объединить с верхнимТекущий элемент сливается с предыдущимprev.span += curr.span, curr удаляется
Объединить с нижнимТекущий элемент сливается со следующимcurr.span += next.span, next удаляется
РазделитьЭлемент с span>1 разбивается обратно на отдельныеСоздаётся по элементу на каждый DOM-блок
УдалитьУдаление из эталонаЭлемент убирается из массива
СоздатьДобавить элемент из неназначенного DOM-блокаНовый элемент с span=1

После каждой операции — перенумерация (renumberRefElements()), перестроение бейджей (rebuildBadges()).

10.4. Синхронизация с DOM

  • PDF-режим: _syncPdfMarkers() — маппинг ref-элементов на .anno-marker по span. Лишние маркеры скрываются, первый маркер в span показывает метку с расширенной скобкой
  • HTML-режим: _syncHtmlElements() — маппинг на top-level блоки с data-anno-idx. Лишние блоки помечаются как data-anno-idx-cleared (доступны для «Создать»)

10.5. Сохранение

Кнопка «Сохранить» → POST /api/reference/<dmc> с JSON-телом → Python записывает в файл с обновлённым modified_at и source: "auto+manual".

11. «Форматировать согласно эталону»

Текущая реализация (бывшая кнопка «Автоулучшение», переименована)

11.1. Общий workflow

Одно-проходный процесс, управляемый из verify_loop.py:

  1. Загрузка эталона из _references/{dmc}.json
  2. Очистка overrides (для backward compatibility)
  3. Конвертация DOCX → XML с применением эталонной разметки
  4. Сравнение с эталоном (LCS-алгоритм)
  5. Валидация XML по XSD
  6. Маппинг ошибок XSD обратно на элементы

11.2. Применение эталонной разметки

Функция apply_reference_markup() в parsers/elements_analyzer.py:1151-1329:

  1. Для каждого ref-элемента ищется лучшее совпадение среди авто-извлечённых по сходству текста (prefix scoring)
  2. Тип из эталона подставляется IN-PLACE (без переупорядочивания элементов)
  3. Элемент помечается метаданными:
    • _ref_annotated: True — тип пришёл из эталона
    • _original_type — исходный авто-определённый тип
    • _ref_idx — индекс в эталоне
    • _ref_type_raw — тип из эталона (сырой)
  4. Если для элемента нет совпадения в эталоне — остаётся авто-определённый тип

11.3. Сравнение через LCS

comparison_app/headless_comparator.py

  • Извлечение последовательности типов элементов из эталона и из XML
  • Вычисление Longest Common Subsequence (LCS) по типам
  • Для совпавших пар — text similarity через difflib.SequenceMatcher
  • Score = 0.7 × (matched / max_count) + 0.3 × avg_text_similarity
  • Диапазон: 0.0 – 1.0

11.4. Маппинг XSD-ошибок

Функция _map_xsd_to_source_elements() в verify_loop.py:51-95:

  • Текстовое сопоставление (prefix, 3-20 символов)
  • Для каждой ошибки — определение:
    • is_user_annotated — элемент пришёл из эталона?
    • user_type — тип по эталону
    • original_type — авто-определённый тип (до override)
    • ref_idx — индекс для навигации

11.5. Отображение результатов

  • Progress bar во время конвертации (polling /api/verify-loop-progress/)
  • Итоговый бейдж: Score % + XSD: PASS или количество ошибок
  • Зелёный если score ≥ 95%, жёлтый если ниже
  • При XSD-ошибках — панель «XSD Issues» со списком, кликабельная навигация к ref-элементу
  • Правая панель обновляется свежим S1000D HTML (/api/s1000d-html/)

Часть III. Критерии качества

Отображение и редактирование разметки

IDТребованиеСтатусКомментарий
11.1 Для всех элементов в PDF должна быть разметка, и она должна соответствовать тому, что отображается в XML (а не вычисляться заново для PDF) Расхождение Текущее: PDF-блоки извлекаются независимо через PyMuPDF и не связаны с XML-элементами. Число блоков и типы не совпадают. Мостом служит эталон (reference), но автоматической синхронизации «PDF-блоков ↔ XML-элементов» нет.
Целевое: Разметка в PDF должна отражать структуру, заданную в XML (или в эталоне как его прообразе).
11.2 Нет «бесхозных» элементов — удаление подразумевает возврат к автоматической разметке Целевое При удалении пользовательской разметки элемент должен получить автоматически определённый тип, а не исчезнуть
11.3 Визуальное различие между пользовательской и автоматической разметкой Целевое Например: пользовательская — сплошная рамка, автоматическая — пунктирная; или цветовое кодирование
11.4 При merge/split/change type — перерисовка разметки всей страницы или документа Частично реализовано rebuildBadges() перестраивает бейджи после операций. Требуется проверка полноты перерисовки

Нумерация остальных элементов не сбивается — точкой отсчёта остаётся исходный документ
