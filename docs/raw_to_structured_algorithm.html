1. Назначение и обзор

Скрипт raw_to_structured.py выполняет преобразование сырой папки с исходными документами (Word, PDF, графика) в двухуровневую структуру папок, соответствующую стандарту S1000D. Каждая папка второго уровня представляет один модуль данных (Data Module) и содержит соответствующие исходные файлы.

Двухэтапный pipeline

1
raw → structured (этот скрипт) Парсинг имён файлов, назначение DMC-кодов, создание папок, копирование файлов.
2
structured → XML (main.py) Чтение документов из структурированных папок, анализ элементов, генерация S1000D XML.

Интерфейс командной строки

python raw_to_structured.py --input <raw> --output <out> python raw_to_structured.py --input <raw> --output <out> --validate <ref>
ПараметрОписание
--inputПуть к сырой папке с исходными документами (например, doc_source_29_raw)
--outputПуть к выходной папке для структурированных данных (например, doc_source_29_generated)
--validateПуть к эталонной папке для валидации результатов (опционально)

2. Двухуровневая структура папок

Выходная структура состоит из двух уровней вложенности:

Level 1 — Компоненты

Формат: {systemCode}-{subSystem}-{component} - {ComponentName}

Пример: 029-11-01 - Гидрокомпенсатор

Level 2 — Модули данных

Формат: [{DMC}] {ComponentName}. {InfoName}

Пример: [S5-A-029-11-01-00A-040A-A] Гидрокомпенсатор. Описание устройства и принципа действия

doc_source_29_generated/ 029-00-00 - Гидравлическая система/ [S5-A-029-00-00-00A-005A-A] Гидравлическая система. Перечень принятых сокращений/ [S5-A-029-00-00-00A-012A-A] Гидравлическая система. Меры безопасности/ [S5-A-029-00-00-00A-040A-A] Гидравлическая система. Описание и принцип действия/ ... 029-11-01 - Гидрокомпенсатор/ [S5-A-029-11-01-00A-040A-A] Гидрокомпенсатор. Описание устройства и принципа действия/ [S5-A-029-11-01-00A-920A-A] Гидрокомпенсатор. Демонтаж и монтаж/ ...

Создание папок и копирование файлов реализовано в функции create_folder_structure(). Имена папок очищаются от недопустимых символов Windows функцией sanitize().

3. Структура DMC-кода

DMC-код (Data Module Code) однозначно идентифицирует каждый модуль данных. Формат строится функцией build_dmc_string() в raw_to_structured.py.

Пример: S5-A-029-11-01-00A-040A-A

S5S5modelIdentCodeКод модели изделия (по умолчанию)
AAsystemDiffCodeКод отличий системы (по умолчанию)
029029systemCodeКод системы (029 = гидросистема)
1111subSystemCodeКод подсистемы (2 цифры: subsystem + sub-subsystem)
0101subSubSystemCode / assyCodeКод компонента/сборки

Поле assyDisassyCode формируется особым образом: если disassy_code != '00', используется disassy_code, иначе — assy_code. К нему всегда добавляется вариант A.

4. Правила назначения info-кодов

Info-код определяется по ключевым словам в заголовке технологической карты (ТК). Функция match_info_code() ищет совпадения в массиве INFO_CODE_RULES и выбирает правило с наивысшим приоритетом.

Каждое правило содержит: обязательные ключевые слова (все должны присутствовать), исключающие ключевые слова (ни одно не должно присутствовать), info-код, вариант и приоритет.

6. Специальные случаи

6.1 ТК ТО — разбиение на 3 модуля

Файл «ТК ТО» (технологическая карта технического обслуживания) автоматически разбивается на 3 отдельных модуля данных. Один и тот же исходный файл копируется в 3 папки:

Info CodeВариантНазвание модуля
012AМеры безопасности

920AОбщие указания при проведении демонтажно-монтажных работ

6.2 ПИУН — разбиение на 5 модулей

Файл ПИУН (перечень используемых узлов и неисправностей) разбивается на 5 модулей данных, все с info-кодом 420A и различными disassyCode (01–05). Рисунки ПИУН привязываются к соответствующему модулю по номеру (рис. 101 → disassyCode 01, рис. 102 → 02 и т.д.).

6.3 Фильтроэлементы

Если в заголовке технологической карты присутствует слово «фильтроэлемент», поле assyCode устанавливается в 01 (вместо стандартного 00). Имя компонента формируется функцией _filter_element_name() как "Фильтроэлемент {название компонента}".

8. Алгоритм валидации

Функция validate_against_reference() сравнивает сгенерированную структуру папок с эталонной (reference). Используется для контроля корректности алгоритма и доступна через CLI-параметр --validate, а также через API-маршрут /api/generate-structure.

Этапы валидации

1
Сбор данных Обход папок Level 1 и Level 2 в обеих директориях. Извлечение DMC-кодов из имён папок L2 функцией extract_dmc_from_folder().
2
Сравнение DMC-кодов Точное совпадение (exact match). Определяются: совпадающие коды, коды только в reference, коды только в generated.
3
Сравнение имён L1 (компоненты) Коды L1 папок (часть до « - ») сравниваются точно. Названия (часть после « - ») сравниваются нечётко через difflib.SequenceMatcher с порогом 0.85.
4
Сравнение имён L2 (модули данных) Для совпадающих DMC-кодов сравниваются заголовки папок L2 (часть после ]) с тем же порогом 0.85.

Нечёткое сравнение имён

Функция _names_match() реализует три стратегии сравнения:

  1. Точное совпадение — после нормализации (lowercase, схлопывание пробелов, удаление завершающих точек)
  2. Prefix match — для усечённых имён Windows (ограничение MAX_PATH). Если короткое имя >= 15 символов и является префиксом длинного — считается совпадением
  3. Fuzzy match — difflib.SequenceMatcher с порогом 0.85
Функция validate_against_reference() возвращает структурированный dict с результатами: количество L1/L2 папок, совпавшие и несовпавшие DMC-коды, расхождения в именах. Это позволяет использовать результат программно (например, в API /api/generate-structure).
